# Deployment Architecture

## 1. Deployment model

The PaaS uses an asynchronous build-and-release pipeline. API requests
create jobs; a separate worker performs long-running operations.

## 2. Constrained MVP build flow

1.  Validate application ownership, Git source, branch and build
    configuration. Only public HTTPS repositories are accepted; URLs
    containing embedded credentials are rejected.
2.  Create a deployment record with a unique ID, or return the existing
    record when the request repeats an already-used idempotency key.
3.  Enqueue a BullMQ job.
4.  Worker selects a healthy runtime node with sufficient free
    resources.
5.  Worker connects through the restricted SSH adapter and starts a
    controlled BuildKit build on that selected node.
6.  Limit the system to one active build at a time in the MVP.
7.  Start the resulting image as a platform-managed container on the
    same node.
8.  Record the image reference and digest, source revision, target node
    and allocated port.

A private OCI registry is deferred because each VM has only a 15 GB disk
and Server 1 must reserve its memory for the control plane and the
existing Apache portfolio. This means images are initially node-local.
Cross-node migration requires rebuilding on the destination node.

## 3. Build isolation and limits

-   Use an isolated build workspace and clean it after completion.
-   Do not build untrusted source with privileged containers or
    unrestricted host mounts.
-   Enforce a 10-minute build timeout, CPU and memory limits, and a 1 GiB
    build cache ceiling per node.
-   Restrict concurrent builds to one.
-   Clean dangling images and build cache according to a documented
    retention policy.
-   Do not allow user-supplied shell commands.

## 4. Scheduling

The first scheduler is a best-available-node selector, not a distributed
cluster scheduler.

Candidate inputs:

-   Node reachable/healthy status
-   Available memory
-   CPU load or utilization
-   Available disk
-   Existing allocated application resource limits
-   Node enabled/disabled state

Reject nodes that are unhealthy or do not satisfy requested resource
limits. Use deterministic tie-breaking so scheduling can be tested. Do
not claim automatic failover or high availability in the MVP.

## 5. Runtime deployment

1.  Worker connects to the selected node using a dedicated SSH account
    whose key is pinned to a forced command, so it cannot open a shell.
2.  Worker requests a narrowly defined build/deployment operation through
    that helper's verb allowlist.
3.  BuildKit builds the application image on that node.
4.  Container starts with a generated name, labels, restart policy,
    resource limits and an allocated host port from the node's
    `30000-32767` range.
5.  Application health check runs.
6.  On success, deployment becomes healthy and routing is updated.
7.  On failure, deployment becomes failed; preserve the last known
    healthy release where possible.

The system must not expose a general-purpose shell endpoint to dashboard
users. Commands and arguments are generated by trusted backend code from
validated fields.

## 6. Runtime port and routing strategy

Each application container receives an allocated host port on its
runtime node. Ports are allocated from `30000-32767`, unique per
`(runtime node, port)`, and bound to the node's private address. The port
must be reachable from Server 1's Traefik host over the private network
and should be blocked from unrelated sources by firewall rules.

Traefik uses its file provider to route each application hostname to the
corresponding private node IP and allocated host port. The worker
generates configuration from validated deployment metadata, writes it
atomically, validates it, and then triggers a safe reload/update.

## 7. Domain strategy

Primary MVP strategy: one subdomain per app, for example
`demo.apps.ogulix.tech`.

Path-based hosting such as `paas.ogulix.tech/apps/demo` is optional and
not guaranteed for every app. It requires the application to support a
configurable base path and correct asset, callback and redirect URLs.

## 8. Deployment states

Canonical state machine:

`QUEUED -> PREPARING -> BUILDING -> STARTING -> HEALTH_CHECKING -> RUNNING`

Failure from any active state transitions to `FAILED`. Cancellation may
transition queued work to `CANCELLED`; active cancellation requires
explicit safe handling. `RUNNING`, `STOPPED`, `FAILED` and `CANCELLED` are
terminal for an individual attempt.

`docs/architecture/deployment-state-machine.md` is the single source of
truth for status names. The earlier `DEPLOYING` and `SUCCEEDED` labels
are withdrawn and must not appear in code or UI.

Store timestamps, source revision, image reference and digest, target
node, allocated port, status transitions and redacted error details.

## 9. Rollback and limitations

Keep the last known healthy deployment reference and image on the same
runtime node. Rollback redeploys that node-local image and restores its
routing after health checks pass.

The initial MVP does not provide seamless cross-node failover because
images are not centrally stored. A private registry or external OCI
registry can be introduced after capacity/storage planning.
